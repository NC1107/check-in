# Running multiple groups on one host

One host can serve several completely independent Check-In groups — one app container,
one database, and one media volume **per group**, each on its own subdomain. Groups are
physically isolated: there is no shared table, no shared media directory, and no way for
one group's members to see another group exists.

```
check-in.example.com          → server-main  → database "checkin"        (your original group)
alpha.check-in.example.com    → server-alpha → database "checkin_alpha"
beta.check-in.example.com     → server-beta  → database "checkin_beta"
```

The same person joining two groups has two separate accounts (one per server) — that is
by design, not a bug.

## How it works

- `groups/` is the registry: one small env file per extra group (slug, display name,
  per-group debug token). Your original group is always included implicitly as `main`
  and keeps its existing database and media volume — **no migration**.
- `scripts/gen-stack.sh` renders the registry into `docker-compose.generated.yml` and
  `Caddyfile.generated`. The hand-written `docker-compose.yml` / `Caddyfile` remain the
  single-group setup; once you use groups, run the generated stack instead:

  ```bash
  docker compose -f docker-compose.generated.yml up -d
  ```

- Backups scale automatically: the generated `db-backup` dumps **every** group database
  and `media-backup` archives **every** media volume. If you add a group by hand,
  re-run `gen-stack.sh` or the new group will silently have no backups.

## Prerequisites

- DNS for the group subdomains. Easiest: one wildcard record
  `*.check-in.example.com → <your server IP>` — then every future group needs no DNS
  work. Per-group `A` records work too. Match whatever proxy/CDN setting your main
  record uses.
- If you front the domain with Cloudflare (or similar), make sure any firewall/geo
  rules are **zone-wide**, not scoped to the main hostname - otherwise new subdomains
  get different (stricter) treatment, which can break app review and leave a group's
  invite page unreachable for the people you send it to.
- Caddy issues a separate Let's Encrypt certificate per subdomain automatically
  (HTTP-01) — no wildcard certificate or DNS plugin needed.

## Adding a group

```bash
./scripts/new-group.sh alpha "Alpha Crew"
docker compose -f docker-compose.generated.yml up -d
```

The script registers the group, creates its database, and re-renders the stack. The new
server initializes its own schema on first boot.

> **Claim the group before you share it.** A brand-new group has no admin: the **first
> phone number to sign up becomes the host**. Open the app, add the group
> (`alpha.check-in.example.com`), and sign up yourself *before* sending anyone the
> invite link. The app warns you when you're about to become a group's host.

Then invite people the same way as your first group: add their phone numbers to that
group's invite list (Admin tab while the group is active), and send them the link:

```
https://alpha.check-in.example.com/join
```

The Admin tab has an **Invite link** row that copies exactly that link for the group
you're managing. The link identifies the server; the phone allowlist still decides who
may sign up. Tapping it opens Check-In with the group's address already filled in, or
offers the App Store / Google Play to anyone who doesn't have the app.

## Removing a group

1. Delete `groups/<slug>.env` and re-run `./scripts/gen-stack.sh`.
2. `docker compose -f docker-compose.generated.yml up -d --remove-orphans` stops the
   group's server.
3. Its database and media volume are **not** deleted automatically. When you're sure:
   ```bash
   docker compose -f docker-compose.generated.yml exec db dropdb -U checkin checkin_<slug>
   docker volume rm check-in_media_<slug>
   ```

## Notes

- **Push notifications**: all groups share the same Firebase project (same app), so the
  one `CHECKIN_FCM_CREDENTIALS_HOST` secret in `.env` serves every group. Notifications
  are titled with the group's display name so members can tell groups apart.
- **Debug view**: each group gets its own `CHECKIN_DEBUG_TOKEN` (generated by
  `new-group.sh`), at `https://<slug>.<domain>/debug?token=…`.
- **Invite links**: each group's server serves its own `/join` page, so there is nothing
  to configure and nothing static to deploy. The page's "Open in Check-In" button uses
  the `checkin://` scheme, which works on any domain on both platforms - no
  `.well-known/` association files, no domain verification.
- **Postgres connections**: each group server keeps its own small connection pool
  against the one Postgres. At friend-group scale (a handful of groups) the default
  `max_connections` is plenty; don't raise per-server pool sizes.
